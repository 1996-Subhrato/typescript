# unknown at the Boundary

## What

The rule that makes every other API topic safe: **anything that enters your program from
outside is `unknown` until you have checked it.**

TypeScript only knows about code it compiled. It cannot see inside a network response, a
file, a form submission, or another window's message. The most honest type for those is
`unknown`, and the work of the boundary is turning `unknown` into a precise type with a
real check.

| Boundary | Examples |
| -------- | -------- |
| HTTP | response bodies, request bodies, query strings, headers |
| Storage | `localStorage`, cookies, files, database JSON columns, caches |
| Messaging | `postMessage`, WebSockets, queues, webhooks |
| Environment | `process.env`, command-line arguments |
| Third-party callbacks | SDK events, plugin hooks |

## Where `any` sneaks in

You rarely write `any`; the standard library hands it to you.

```ts
async function loadUser(response: Response) {
  const user = await response.json(); // Promise<any> -> user is `any`

  const nonsense: number = user.name.deeply.nested(); // compiles
  return user.id.toFixed(2); // compiles; crashes if `id` is a string
}
```

`JSON.parse`, `Response.json()`, `Request.json()` and event `data` all return `any`. Once a
value is `any`, everything derived from it is too. Stop it at the door by assigning to
`unknown`:

```ts
async function loadUser(response: Response) {
  const user: unknown = await response.json();

  return user.id; // Error: 'user' is of type 'unknown'
}
```

Now the compiler refuses to let you touch the value until you check it.

## Four ways to narrow `unknown`

### 1. Inline checks

Fine for a field or two:

```ts
function readTotalCents(body: unknown): number | undefined {
  if (typeof body !== "object" || body === null) return undefined;
  if (!("totalCents" in body)) return undefined;

  const value = body.totalCents; // unknown, but now known to exist
  return typeof value === "number" ? value : undefined;
}
```

### 2. Small helpers

Extract the repeating checks:

```ts
function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null && !Array.isArray(value);
}

function readString(source: Record<string, unknown>, key: string): string | undefined {
  const value = source[key];
  return typeof value === "string" ? value : undefined;
}

function readNumber(source: Record<string, unknown>, key: string): number | undefined {
  const value = source[key];
  return typeof value === "number" ? value : undefined;
}

type Product = { id: string; priceCents: number };

function parseProduct(input: unknown): Product | undefined {
  if (!isRecord(input)) return undefined;

  const id = readString(input, "id");
  const priceCents = readNumber(input, "priceCents");
  if (id === undefined || priceCents === undefined) return undefined;

  return { id, priceCents };
}
```

### 3. Type guards and assertion functions

Wrap the check so callers get narrowing ([*Type Guards & Predicates*](/docs/type-guards)):

```ts
type Product = { id: string; priceCents: number };

declare function parseProduct(input: unknown): Product | undefined;

function isProduct(input: unknown): input is Product {
  return parseProduct(input) !== undefined;
}

function assertProduct(input: unknown): asserts input is Product {
  if (!isProduct(input)) throw new Error("Response is not a Product");
}

function handle(body: unknown): string {
  assertProduct(body);
  return `${body.id}: ${body.priceCents}`; // body: Product from here on
}
```

### 4. A schema

For anything with more than a few fields, nesting, defaults or conversions, let a schema
describe the shape once ([*DTOs & Runtime Validation*](/docs/dtos-and-validation)):

```ts
import { z } from "zod";

const ProductSchema = z.object({
  id: z.string(),
  priceCents: z.number().int().nonnegative(),
  createdAt: z.iso.datetime().transform((value) => new Date(value)),
});

type Product = z.output<typeof ProductSchema>; // createdAt: Date
type ProductWire = z.input<typeof ProductSchema>; // createdAt: string

function parseProduct(input: unknown): Product {
  return ProductSchema.parse(input); // throws on a bad shape
}
```

Notice two types come out of one schema: `z.input` is what is on the wire (a string) and
`z.output` is what you get after conversion (a `Date`). The date conversion happens at the
boundary, where [*Typing API Responses*](/docs/typing-api-responses) said it belongs.

## Choosing

| | Inline / helpers | Guard | Schema |
| --- | --- | --- | --- |
| Setup | none | small | a dependency |
| Type and check can drift apart | yes | yes | **no** |
| Error messages | write them | write them | automatic, with paths |
| Conversions (dates, defaults) | manual | manual | built in |
| Best for | 1-3 fields | one-off checks | real payloads |

If the same shape is written twice — once as a `type`, once as a check — one of them will
eventually be wrong. A schema removes the second copy.

## From a schema to a `Result`

Adapt the schema's `safeParse` to the `Result` shape the rest of your code uses:

```ts
import { z } from "zod";

type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

export function parseWith<S extends z.ZodType>(
  schema: S,
  input: unknown,
): Result<z.output<S>, string[]> {
  const parsed = schema.safeParse(input);
  if (parsed.success) return { ok: true, value: parsed.data };

  return {
    ok: false,
    error: parsed.error.issues.map((issue) => `${issue.path.join(".")}: ${issue.message}`),
  };
}

const UserSchema = z.object({ id: z.string(), email: z.email() });

const result = parseWith(UserSchema, { id: "usr_1", email: "not-an-email" });
if (!result.ok) console.log(result.error); // ["email: Invalid email address"]
```

## Strict or lenient?

Decide what to do with fields you did not ask for.

- **Lenient (Zod's default):** unknown keys are ignored and removed from the result. This is
  the right default for responses: when the server adds a field, your client keeps
  working.
- **Strict:** unknown keys are an error. Useful for **requests you receive**, where an
  unexpected field often signals a client bug or an attack.

Require only what you actually use. Validating a 40-field response to read 3 fields makes
your client break whenever the server changes something irrelevant.

## But I own the server

Fair question; sharing types between client and server ([*Modelling an API Contract*](/docs/api-contract-modelling))
removes drift in the *source*. It does not remove:

- **Deploy skew:** an old client talking to a new server, or the reverse.
- **Proxies, CDNs and caches** returning stale or error pages.
- **Bugs** that make the server send something it should not.

A reasonable compromise: validate always at the edges you do not control, and validate
internal APIs at least in development and tests (a failing check there is a contract bug,
found early).

## Where `as` is acceptable

After the check. `parseStatus` in [*Typing API Responses*](/docs/typing-api-responses) casts to `KnownStatus` immediately
after `includes` proved it. What is never acceptable is `await response.json() as T` with
nothing in between.

## Common mistakes

- **`as T` on `response.json()`** — the original sin.
- **Using `any` for "temporary" parsing code.** It does not stay temporary.
- **Validating after use.** Check first, then pass the narrowed value onward.
- **Hand-writing a type and a validator separately.**
- **Throwing a raw `ZodError` to the UI** instead of mapping it to your error type.
- **Validating the whole payload** when only a few fields are used.
