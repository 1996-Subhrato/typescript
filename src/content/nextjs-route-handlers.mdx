# Route Handlers

## What

A **Route Handler** is an HTTP endpoint inside the App Router: a `route.ts` file that
exports a function named after an HTTP method. It is Next.js's equivalent of an Express
route, built on the standard web `Request` and `Response` types.

```ts title="app/api/health/route.ts"
export async function GET(): Promise<Response> {
  return Response.json({ status: "ok" });
}
```

Supported method names: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`. Any other
method returns `405`. A `route.ts` cannot sit in the same segment as a `page.tsx`.

> Unlike Express, there is no `req`/`res` pair. A handler receives a `Request` and
> **returns** a `Response`. That is simpler to type: the return value is the response.

## `NextRequest` and `NextResponse`

Next.js extends the web types with conveniences: `request.nextUrl`, `request.cookies`, and
`NextResponse`, whose `json` method is generic over the body.

```ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

type Product = { id: number; name: string };
type ApiError = { error: string };

const products: Product[] = [{ id: 1, name: "Keyboard" }];

export async function GET(request: NextRequest): Promise<NextResponse<Product[] | ApiError>> {
  const query = request.nextUrl.searchParams.get("q"); // string | null

  if (query !== null && query.length > 50) {
    return NextResponse.json({ error: "Query too long" }, { status: 400 });
  }

  const matches = query === null ? products : products.filter((p) => p.name.includes(query));
  return NextResponse.json(matches);
}

export async function POST(): Promise<NextResponse<Product[] | ApiError>> {
  return NextResponse.json({ id: 1 }); // Error: '{ id: number }' is not a Product[] or an ApiError
}
```

Annotating the return type as `NextResponse<Success | Failure>` makes the compiler check the
body of every `NextResponse.json(...)` call. A handler can no longer drift from its contract.

## Route parameters

`params` is a Promise, exactly as in pages. Put it in the second argument:

```ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

type Context = { params: Promise<{ id: string }> };

export async function GET(_request: NextRequest, { params }: Context): Promise<NextResponse> {
  const { id } = await params;
  const numericId = Number(id);

  if (!Number.isInteger(numericId)) {
    return NextResponse.json({ error: "id must be an integer" }, { status: 400 });
  }
  return NextResponse.json({ id: numericId });
}
```

Next.js also generates a global `RouteContext` helper, so the route string defines the
shape:

## The request body is `unknown`

`request.json()` is declared to return `Promise<any>`. Do not let that `any` leak:

```ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";
import { z } from "zod";

const CreateProductSchema = z.object({
  name: z.string().min(1),
  priceCents: z.number().int().nonnegative(),
});

type Product = z.infer<typeof CreateProductSchema> & { id: number };

export async function POST(request: NextRequest): Promise<NextResponse<Product | { error: string }>> {
  let body: unknown;
  try {
    body = await request.json(); // assign to `unknown`: nothing is trusted yet
  } catch {
    return NextResponse.json({ error: "Body must be valid JSON" }, { status: 400 });
  }

  const parsed = CreateProductSchema.safeParse(body);
  if (!parsed.success) {
    return NextResponse.json({ error: "Invalid product" }, { status: 400 });
  }

  return NextResponse.json({ id: 1, ...parsed.data }, { status: 201 });
}
```

The pattern is the one from *DTOs & Runtime Validation*: `unknown` in, schema in the
middle, a checked type out. The `try/catch` is separate because malformed JSON throws before
validation begins.

## Cookies and headers are asynchronous

In Next.js 16, `cookies()` and `headers()` return Promises:

```ts
import { cookies } from "next/headers";
import { NextResponse } from "next/server";

export async function GET(): Promise<NextResponse> {
  const cookieStore = await cookies();
  const token = cookieStore.get("session")?.value; // string | undefined

  if (token === undefined) {
    return NextResponse.json({ error: "Not signed in" }, { status: 401 });
  }
  return NextResponse.json({ signedIn: true });
}
```

Forgetting `await` gives you a Promise where you wanted the store, and the compiler says so.

## Sharing the contract with the client

The point of typing a handler is that the browser code calling it can use the same types.
Keep the response types in a shared module.

```ts
export type Product = { id: number; name: string };

export type ApiError = { error: string };

export type ProductsResponse = { products: Product[] };
```

```ts
type Product = { id: number; name: string };
type ProductsResponse = { products: Product[] };

declare function isProductsResponse(value: unknown): value is ProductsResponse;

export async function fetchProducts(): Promise<Product[]> {
  const response = await fetch("/api/products");
  const body: unknown = await response.json();

  if (!isProductsResponse(body)) throw new Error("Unexpected response shape");
  return body.products;
}
```

The server declares what it sends; the client still **validates** what arrives. Sharing the
type removes drift, not the need to check. *Real-World API Typing* builds this into a
reusable client.

## Common mistakes

- **Using `req.body` / `res.json()` habits from Express.** Here you return a `Response`.
- **`await request.json()` assigned to a typed variable.** It silently trusts the client.
- **Forgetting that `params`, `cookies()` and `headers()` are Promises.**
- **Both `page.tsx` and `route.ts` in one segment.** Not allowed.
- **Assuming `GET` handlers are cached.** They are not by default.
- **Returning a plain object** instead of `Response.json(...)`.

## Practice

1. Write `DELETE /api/products/[id]`: validate the id, return `204` with no body, `404` if
   unknown, using an explicit `NextResponse<{ error: string } | null>` return type.
2. Write `GET /api/products` accepting `?page=` and `?pageSize=` parsed with a Zod schema using
   `z.coerce.number()`.
3. Turn the `ProductsResponse` check into a Zod schema shared by the route and the client.
