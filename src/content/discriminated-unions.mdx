# Discriminated Unions

## What

A union of object types that all share one property — the **discriminant** — whose value
is a different literal in each member. Checking that property narrows the whole object.

It is the most useful modelling pattern in TypeScript.

## The problem it solves

The usual JavaScript approach is a bag of optional fields:

```ts
type PaymentResult = {
  success: boolean;
  transactionId?: string;
  error?: string;
};

const bad: PaymentResult = { success: true, error: "Card declined" }; // allowed, and nonsensical
```

Nothing stops "success with an error" or "failure with a transaction id". Every consumer
must guess which fields are valid.

## The pattern

```ts
type PaymentResult =
  | { status: "success"; transactionId: string }
  | { status: "failed"; reason: string }
  | { status: "pending" };

function describe(result: PaymentResult): string {
  switch (result.status) {
    case "success":
      return `Paid: ${result.transactionId}`; // result: the success member
    case "failed":
      return `Failed: ${result.reason}`; // result: the failed member
    case "pending":
      return "Waiting for the bank";
  }
}
```

Each member now carries *exactly* the fields that make sense for it. Accessing a field
from the wrong case is an error:

```ts
type PaymentResult =
  | { status: "success"; transactionId: string }
  | { status: "failed"; reason: string };

function reason(result: PaymentResult): string {
  return result.reason; // Error: 'reason' does not exist on type success member
}
```

## Exhaustiveness checking

Add `assertNever` to turn a forgotten case into a compile error rather than a runtime
surprise.

```ts
type PaymentResult =
  | { status: "success"; transactionId: string }
  | { status: "failed"; reason: string }
  | { status: "refunded"; amount: number };

function assertNever(value: never): never {
  throw new Error(`Unhandled case: ${JSON.stringify(value)}`);
}

function describe(result: PaymentResult): string {
  switch (result.status) {
    case "success":
      return `Paid: ${result.transactionId}`;
    case "failed":
      return `Failed: ${result.reason}`;
    default:
      return assertNever(result); // Error: refunded member is not assignable to 'never'
  }
}
```

Add a new status to the union and the compiler lists every `switch` that has not been
updated. This turns refactoring from "hope you found them all" into "fix the red
squiggles".

## Real-world example: async UI state

```ts
type LoadState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "success"; data: T };

type Product = { id: number; name: string };

function render(state: LoadState<Product[]>): string {
  switch (state.status) {
    case "idle":
      return "";
    case "loading":
      return "Loading...";
    case "error":
      return `Failed: ${state.message}`;
    case "success":
      return state.data.map((product) => product.name).join(", ");
  }
}
```

Compare with `{ loading: boolean; error?: string; data?: Product[] }`, which allows
`loading: true` together with `data`. The union makes those states unrepresentable.

The same shape drives Redux/`useReducer` actions:

```ts
type CartAction =
  | { type: "add"; sku: string; quantity: number }
  | { type: "remove"; sku: string }
  | { type: "clear" };

function reducer(items: Record<string, number>, action: CartAction): Record<string, number> {
  switch (action.type) {
    case "add":
      return { ...items, [action.sku]: (items[action.sku] ?? 0) + action.quantity };
    case "remove": {
      const { [action.sku]: _removed, ...rest } = items;
      return rest;
    }
    case "clear":
      return {};
  }
}
```

(`Record<string, number>` is a dictionary type, covered in *Utility Types*.)

## Requirements

- The discriminant must be a **literal type** (`"success"`, `1`, `true`) — not `string`.
- Every member must have it, with the same property name.
- Conventional names: `type`, `kind`, `status`. Pick one per codebase.

## Common mistakes

- **Typing the discriminant as `string`.** Then there is nothing to narrow on.
- **Optional fields instead of separate members.** This is the pattern you are replacing.
- **A `default` branch that returns something.** It hides new cases. Use `assertNever`.
- **Over-modelling.** Two states with one differing field might just be an optional.
  Use a union when the *combinations* of fields matter.

## Practice

Model a notification:

- `email` — has `address` and `subject`
- `sms` — has `phoneNumber`
- `push` — has `deviceToken` and `badgeCount`

Write `send(notification): string` using a `switch` and `assertNever`. Then add a
fourth kind and watch the compiler find your `switch`.
