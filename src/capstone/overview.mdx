# The Orders Desk

## What you will build

A small orders system, typed end to end: customers place orders, an operator lists them and
cancels the ones that can still be cancelled. It is 14 files, and every one of them is
shown on these pages.

It is small on purpose. The point is not the feature list; it is that **one idea flows through
every layer**: a single description of the API produces the types for the client, the server
and the UI, and nothing is written twice.

## Three rules the whole project follows

1. **One source of truth.** The wire format is described once, as schemas. The client's
   types, the server's types and the response parsing all come from that description.
2. **Failure is data.** Anything that can reasonably go wrong comes back as a value
   (`Result` with a typed error), not as an exception, so the compiler makes every caller
   decide what to do.
3. **Check at the edge, trust inside.** Everything that arrives from outside the program
   (a response body, a request body) starts as `unknown` and is validated once. After that,
   the types are believed.

## How the pieces fit

```text
  UI (React)                 Client                  Server
  ----------                 ------                  ------
  OrdersDesk  --call()-->    createClient  --HTTP--> Next.js route files
  reducer                    parses responses         |
                             into domain types        v
                                                     Handlers  (one per route, checked
                                                     |          against the contract)
                                                     v
                                                     Service   (business rules, Result)

  Shared by all of them:  Contract (schemas + routes)  .  Domain types  .  Result  .  ApiError
```

## The files

```text
src/
  shared/
    result.ts            Result, ok, err, assertNever
    api-error.ts         ApiError, toApiError, messageFor
  domain/
    order.ts             Order and friends, branded Cents and OrderId
  contract/
    schemas.ts           wire-format schemas, and the conversion to domain types
    routes.ts            the route table and the types derived from it
  client/
    api-client.ts        createClient: a typed call()
  server/
    orders-service.ts    business rules
    http.ts              domain errors -> HTTP responses
    handlers.ts          one handler per route, checked against the contract
    instance.ts          the process-wide service and handlers
  app/api/orders/
    route.ts             Next.js: GET (list) and POST (create)
    [id]/route.ts        Next.js: GET (one order)
  ui/
    orders-state.ts      the reducer and its states
    OrdersDesk.tsx       the React component
```

## How to work through it

- **Type the files yourself** rather than pasting them. The point is to feel where the compiler
  helps. If you do paste, read each file before moving on.
- **Build in order.** Each step only imports files from earlier steps.
- **Run the compiler after every file:** `npx tsc --noEmit`.
- **Do the "Try breaking it" section** at the end of each step. Each lists a change to make and
  the error the compiler gives. Reading those errors is half of what this exercise teaches.
- **The stretch tasks have no solutions**, like every Practice section in the course. Try
  them, and bring your attempts for review.

## Before you start

You need a TypeScript project with `strict` on, and one dependency:

```bash
npm install zod
```

The Next.js route files and the React component assume Next.js 16 and React 19. The other
files do not depend on either, so you can build everything up to Step 5 in any TypeScript
project. These settings from this site's `tsconfig.json` matter for the code to behave as shown:
`strict`, `noUncheckedIndexedAccess`, and `verbatimModuleSyntax`
(see [Strictness Flags](/docs/strictness-flags)).

## What has been checked

This is not sample code that merely looks right.

- All 14 files compile together as one project under `strict` plus `noUncheckedIndexedAccess`,
  `verbatimModuleSyntax`, `noUnusedLocals` and `noUnusedParameters`. The code blocks on these
  pages are compiled as that project by this site's content check, so a page cannot drift from
  code that builds.
- The project was also **run**, end to end: the typed client talking through a fake `fetch`
  to the real handlers and service, covering success, validation errors, a missing order,
  cancelling twice, a network failure, a malformed response and a server error.
- The React component and state machine pass this repository's lint rules for hooks.
- Every error message quoted in the "Try breaking it" sections was produced by making that
  exact change to the project. Those scratch snippets are deliberately broken and import files
  from the project, so the site's content check skips them (they are marked as skipped there);
  the messages come from the real runs instead.
